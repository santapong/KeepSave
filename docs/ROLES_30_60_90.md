# KeepSave — Per-Role 30/60/90 Action Plan (Phase A: MVP Hardening)

Companion to `docs/ROLES.md`. That doc defines *who* does what; this one defines *what they do first*. It turns the roles plan into a 30/60/90 with concrete deliverables, so the plan can be acted on instead of just admired.

> **Phase A reality check.** The team for this phase is: 1 Tech Lead, 1 Backend, 1 Frontend, part-time Security, part-time DevOps, shared QA. PM / UX / Technical Writer slots are **not yet hired**. For un-staffed roles below, the **Interim owner** column says who carries the responsibility until a real hire — usually the Tech Lead or the closest engineer. Don't pretend the work doesn't exist just because nobody is titled for it.

---

## How to use this plan

- **Review cadence:** every 30 days at a standing planning meeting. Each role reports done / in-progress / blocked against this list. Slipped items either move to the next bucket *with a written reason* or are explicitly killed (and the reason logged).
- **Re-plan triggers:** a Type-1 decision changes scope, an incident exposes a missing capability, or a new hire onboards. Don't re-plan more often — churn is itself a cost.
- **Dependencies:** items marked **[gates]** block another role's work. Items marked **[needs]** depend on another role's deliverable.
- **Definition of done:** a task is done when (a) the artifact exists in the repo, (b) it's been used at least once for its intended purpose, and (c) at least one other role has reviewed it. Existence alone is not done.

## Cross-role gates & dependencies (the critical chain)

These are the dependencies that, if missed, will block other roles. Watch them weekly.

1. **Threat-model refresh (Security, 30d) → Backend negative-auth tests (Backend, 30d).** Backend can't write good negative tests without knowing the attacker model.
2. **RFC process (Tech Lead, 60d) → Backend schema prep (Backend, 90d).** Multi-tenant schema is Type-1; it needs the RFC process to land first.
3. **Key-rotation automation (DevOps, 60d) → Security drill (Security, 60d).** Drill can't be real without the script.
4. **Pentest run (Security, 90d) → QA regression suite (QA, 90d).** QA can't write regression tests for findings until findings exist.
5. **CSP doc (Frontend, 60d) → Public security posture page (Tech Writer/Tech Lead, 60d).** External-facing security claims need the CSP guarantee behind them.

## What this plan deliberately does *not* include

The 30/60/90 isn't a wishlist. The following are real needs but **explicitly deferred** to Phase B (with a one-line reason):

- **Multi-tenant runtime** — Phase B scope; we only do additive schema prep in Phase A.
- **SSO / SAML integration** — waiting on customer demand signal (PM 30d output).
- **Mobile / native SDK** — embed widget covers the web case; mobile is later.
- **GUI-driven approval policies** — current code-driven policy is sufficient until Phase B.
- **i18n** — single-locale English is fine for the current customer set.

If something here gets pulled into Phase A, *something else has to be pushed out*. Don't expand the plan silently.
