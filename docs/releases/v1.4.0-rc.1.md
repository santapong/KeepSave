## What changed since v1.3.0

- Password, Google and GitHub identity flows with stable provider subjects,
  canonical emails, explicit account linking and revocable 24-hour sessions.
  Real Google/GitHub applications and consent/callback acceptance are pending.
- Explicit transactional workspaces, operator-issued user-ID grants, stronger
  current-membership checks and scoped API-key/lease/token enforcement.
- PostgreSQL immutable secret history, restoration as a new revision, retained
  keys across rotation, transaction-aware promotions and encrypted tombstones.
- Recoverable encrypted bundles, metadata previews, selected restoration, an
  isolated-target recovery command and a durable private backup worker.
- Required audit and outbox writes commit with core mutations; the audit-chain
  head is serialized in PostgreSQL. Grant revocation works across API instances.
- A maintained core OpenAPI contract and generated frontend types, compatible
  bounded SDK batch reads, client cache clearing and a local standalone Go SDK.
- Accepted Event Horizon/Field Twist identity, account/session controls and
  secret history/recovery screens; setup and architecture documentation match
  the restricted core's actual availability.
- Go 1.27.1 and Node 24.21.0 build/CI pins, patched dependencies, digest-pinned
  runtime images and expanded synthetic database/security checks.

## Compatibility and safe upgrade

1. Back up the vault and verify recovery into an isolated PostgreSQL target
   using the installation's documented key material before a live cutover.
2. Drain older APIs and writers. Resolve canonical-email collisions before
   migration; never automatically merge accounts or enroll configured admin
   emails as operator grants.
3. Apply additive migrations and explicitly enroll existing vault ciphertext
   as a labeled baseline. Retain historical keys, journal records and snapshots.
4. Require users to authenticate again. Existing untracked human JWTs are
   refused; no cookies or human refresh-token flow are added.
5. Roll back only to a reviewed binary supporting tracked sessions and the
   current journal/key format. An old binary is not a supported rollback target.

The management API remains `/api/v1`. SQLite and MySQL retain bounded legacy
compatibility; versioned vault, recovery and durable jobs are PostgreSQL-only.
Unsupported history/recovery operations return explicit capability refusal.
Backup scheduling/retention stays disabled until installation-specific recovery
acceptance is recorded. Recovery never recreates source sessions or authority.

[ADR-0028](../adr/0028-core-identity-and-vault-release.md),
[ADLC stages 7–8](../ADLC.md) and [release rituals](../ROLES.md) define these
gates. Sponsor-directed integration does not mark them complete. The planned

The restricted core refuses API-host MCP execution, legacy OAuth issuance,
experimental AI/analytics, unenforced policy controls, enterprise SSO/compliance,
non-durable webhooks, event replay and plugin execution. Standards-based MCP,
the GitHub App broker/isolated runner, private skills/Codex profiles and complete
self-hosted team operation remain M2–M5. Social GitHub login is separate from a
GitHub App connection.

adds proposed setup, lifecycle, team and diagnostic slices without claiming
those future features have been implemented.
